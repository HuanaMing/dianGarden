# 無人機任務與動畫系統重構規格

- 狀態：已獲使用者批准，規格建立中；尚未開始重構程式。
- 方案：B，分階段重構、逐步替換。
- 主要程式：`src/game.js`、`src/sky-world.js`。
- 關聯問題：任務255無人機瞬移、工作交接時高度跳變、尋路失敗備援可能穿越障礙、派工停滯風險。
- 原則：先建立可測試的契約與基準，再小步遷移；不一次性推翻整個系統，不引入新依賴。

## 1. 目標與非目標

### 目標
1. 將任務生命週期、派工決策、無人機運行狀態、空間位置／路徑與動畫呈現分離。
2. 統一播種、澆水、採收任務的開始、提交結果、完成、返航與失敗處理。
3. 確保任何工作動畫切換都從當前真實位置連續開始，工作高度改變時以明確的移動段銜接，不直接跳座標。
4. 確保每個任務結果最多提交一次，回呼重複或過期時不重複扣款、澆水、播種或收成。
5. 尋路失敗時不穿越障礙，也不讓整條派工佇列卡死。
6. 保留最多 8 台無人機、多機並行、自動模式、電量／充電、平台移動、存檔與離線模擬的既有玩法。
7. 以可自動重現的回歸測試及診斷紀錄降低日後排錯成本。

### 非目標
- 不重寫 WebGL 渲染器或花卉模型。
- 不改變遊戲經濟、種植時間、澆水規則、無人機購買價格與上限。
- 不新增框架、套件或伺服器。
- 不把短期診斷 log 當成正式任務資料，也不將無人機即時位置加入存檔，除非後續證明必要並另行評估相容性。

## 2. 現況與問題線索

- `src/game.js` 目前承擔工作佇列、選機、電量、作物狀態、任務結果及動畫回呼接線。
- `src/sky-world.js` 目前承擔無人機座標、尋路、巡航／工作高度、飛行動畫與工作特效。
- 兩者透過回呼交接工作結果及返航狀態，造成「工作已完成」和「整趟飛行結束」容易混淆。
- 使用者觀察到採收完成後瞬移，也觀察到播種後無人機跳到同一地塊較高處開始澆水。這些案例提示應檢查跨工作階段的位置與高度連續性，但尚未證明它們必定只有一個根因。
- 任務255曾遇到「尋路失敗即拒絕動畫並中斷佇列」導致無人機停滯的回歸；目前直線備援雖能避免部分停滯，卻有穿越障礙風險，屬暫時措施。
- 在完成基準測試前，不得把靜態來源斷言當成瀏覽器行為驗收。

## 3. 目標分層

### A. 任務管理器（`game.js` 既有邏輯逐步收斂）
負責任務建立、排隊、取消、挑選可執行任務、重試與結果提交。任務是遊戲邏輯資料，不負責計算 3D 座標，也不直接推進動畫時間。

任務建議欄位（先作為內部契約，實作前依現況校準）：
- `id`：執行期間唯一識別。
- `kind`：`plant | water | harvest`。
- `plotIndex`：目標地塊索引；每次使用前確認目標仍有效。
- `status`：`queued | assigned | running | result_committed | succeeded | failed | cancelled`。
- `droneId`：執行中的無人機識別；未派發時為空。
- `attempt`、`createdAt`、`lastError`：重試及診斷資訊。
- `resultCommitted`：防止結果重複提交的保護；不得只靠動畫回呼是否被呼叫判斷。

不要求把這些執行期欄位寫入存檔。先保留現有存檔格式。

### B. 無人機狀態機
每台無人機在任一時刻只有一個主要狀態：
`docked`、`idle`、`outbound`、`working`、`returning`、`charging`、`waiting_path`、`disabled`。
實際狀態命名可在階段一盤點後調整，但不可同時以多個互相矛盾的旗標表示主要階段。

合法主流程：
`idle → outbound → working → returning → idle/charging`。
路徑無法規劃時進入 `waiting_path`，以退避／重試策略處理；不得假裝飛行成功，也不得阻斷其他無關無人機的派工。
任務完成與返航完成是兩個不同事件。工作結果提交後，無人機仍可處於 `returning`。

### C. 位置與路徑控制器（`sky-world.js`）
唯一負責更新無人機世界座標與朝向。動畫層不能自行改寫座標；新飛行段必須從控制器當下位置建立。
路徑包含明確起點、終點、起始高度、目標高度及本段專屬進度。重規劃時建立新段並將本段進度歸零，不可把舊段 elapsed 套用到新路徑。
平台移動後更新目的地；若無安全路徑，停留在安全位置並回報等待重試，不走穿牆直線。
工作高度由單一規則計算：以地塊高度、作物模型高度和工作類型得出目標高度；不同工作高度間以受控垂直／平滑移動段銜接。

### D. 動畫呈現層
只接收「飛行中／工作中／等待／返航」等狀態與進度，呈現機身、旋翼、播種、澆水、採收特效。
動畫開始或結束不能自行派發下一個任務、提交作物結果或將無人機傳送到新座標。
同一幀中狀態變更最多只會建立一個下一階段；所有回呼需有任務識別及一次性防護。

## 4. 事件與交接契約

統一事件語意：
1. `taskAssigned`：派工器已將任務交給某台無人機。
2. `routeStarted` / `routeBlocked`：飛行段已開始／無安全路徑可用。
3. `arrivedAtPlot`：到達工作位置。
4. `workStarted`：工作動畫開始。
5. `workResultCommitted`：作物／金幣等遊戲結果只在此提交一次。
6. `workVisualCompleted`：工作特效完成，不代表返航完成。
7. `returnStarted` / `returnCompleted`：返航開始／完成。
8. `taskSucceeded`、`taskFailed`、`taskCancelled`：任務終態，只能進入一次。

事件名稱可依現有函式風格調整，但語意必須保持分離。避免以一個 `finish()` 同時代表工作完成、釋放任務、返航完成和再次派工。

## 5. 派工與失敗政策

- 同一台無人機同一時間最多執行一個任務。
- 同一任務同一時間最多被一台無人機持有。
- 電量低於既有工作門檻時，不派發新工作；返航／充電優先規則需以既有遊戲行為為基準固定成測試。
- 任務因路徑阻塞而等待時，不得永久丟失；採用有上限的退避重試或事件觸發重試，並繼續派發其他可執行任務。
- 不使用無限制的同步重試迴圈；重試失敗必須產生可診斷狀態。
- 直線路徑只可在經證明沒有障礙且符合碰撞規則時作為安全路徑，不可作為 A* 失敗的通用備援。
- 任務目標已失效（地塊不存在、狀態已變更、作物已被其他任務處理）時，依任務種類安全取消或重排，避免重複結果。

## 6. 座標連續性與診斷

每個動畫階段交接記錄：時間、droneId、taskId、舊／新狀態、舊／新階段、交接前後的 `x,y,z`、路徑段 ID、進度與目的地。
- 正常階段切換不允許直接改變世界座標。
- 飛行更新的單幀位移門檻須以目前速度、frame delta 及速度上限推導；先使用任務255的 0.75 世界單位診斷門檻作為警報值，不可在未校準前直接當成普遍硬性限制。
- 若確定需要瞬間調整模型錨點或工作高度，必須區分「模型相對偏移」與「無人機世界位置」，並有測試說明。
- 診斷預設關閉，可由既有 `sky-garden-drone-debug-v1` 開啟；避免常態大量輸出。

## 7. 分階段執行計畫

### 階段 1：盤點、基準與可重現測試
整理目前呼叫鏈、狀態欄位、回呼責任及失敗路徑；建立最小可測試的狀態快照與連續性測試。先驗證現有派工是否能恢復工作、列出目前回歸風險。不得先改寫核心行為。

### 階段 2：任務生命週期與派工邊界
把任務狀態、一次性提交、取消／失敗／重試語意明確化；將任務完成與返航完成分離。保留既有遊戲規則及存檔格式。

### 階段 3：狀態機與空間運動控制
建立唯一狀態轉換入口，讓座標／航線／工作高度轉換有單一負責者；安全處理路徑失敗與平台移動。先用測試證明不瞬移與不穿越障礙。

### 階段 4：逐步替換工作動畫
依序接通飛行、播種、澆水、採收、返航；每種工作獨立驗收，再測試跨工作接續與多機併行。刪除舊邏輯前需確認沒有其他呼叫者依賴。

### 階段 5：整合回歸與文件收尾
跑完整桌面／手機 Playwright、語法與來源檢查，驗收多機、自動模式、電量、存檔、離線模擬與 WebGL fallback；更新架構文件及任務結果。實機視覺驗收另行標示。

## 8. 驗收標準

### 正確性
- 播種→澆水、澆水→採收、採收→返航、同地塊連續任務等交接不發生座標跳變。
- 任務結果最多提交一次；動畫重複回呼不造成重複扣款／種植／澆水／收成。
- 任務終態不可重新進入執行中；無效任務會安全取消或重排。
- 尋路失敗時無人機不穿越障礙，且其他無人機與可行任務仍能繼續。
- 平台移動時返航目的地更新，重規劃從當前座標與當前高度連續起步。
- 工作高度依地塊／花卉高度正確計算，切換高度有連續運動。

### 多機與遊戲相容
- 1 台與最多 8 台無人機的派工都可運作。
- 返航、低電量、充電與待辦工作不會互相卡死。
- 自動模式的播種／澆水／採收行為與現有規則一致。
- 遊戲重新載入後存檔相容；離線模擬仍按既有規則運作。
- WebGL 不可用時，既有快捷操作及遊戲邏輯仍可使用。

### 測試要求
- Node JavaScript 語法檢查。
- 專門的無人機狀態／路徑單元或可重現測試（沿用現有測試方式，不新增框架）。
- `tests/browser-smoke.mjs` 桌面與手機 Playwright 回歸。
- 記錄測試命令、實際結果、未涵蓋項目；不把來源字串斷言當成動態行為測試。
- 最終使用者視覺驗收需確認播種後澆水、採收後返航、多機同地塊接續等場景。

## 9. 風險與回復策略

- 每個階段獨立提交，測試失敗時只回復該階段的變更。
- 不改存檔格式、不更改經濟參數。
- 不在測試未通過時刪除舊路徑；新舊流程短期共存時須明確指定單一入口，避免雙重更新座標。
- 先修正「路徑失敗停工」與「直線備援穿障」的矛盾，再移除相應舊程式。
- 每階段結束記錄尚未解決的風險；只有完成該階段驗收才開始移除相依的舊程式。

## 10. 本規格的決策邊界

已批准：分階段重構、分離任務／狀態／位置／動畫責任、建立測試及回歸驗收。
仍需先檢查再決定：是否新增獨立 JS 模組、具體狀態欄位名稱、路徑重試間隔、單幀位移門檻、是否需要儲存任何無人機執行狀態。優先採用原生 JavaScript 與既有檔案結構，除非程式盤點證明拆檔有明顯收益。
